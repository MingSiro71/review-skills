# 概要

現ブランチの変更（`origin/<base>...HEAD` の diff）をレビューし、読者が対応判断を下すための文書として
`~/.claude/projects/<slug>/docs/review-<pr番号>-<連番>.md` に書き出す。

プロセスは3段階（前処理を1つ挟む）:

0. **ルール所在の特定**（前処理） — 照合先になる明文ルールのファイルパスだけを1体に集めさせる
1. **配布レビュー** — 8つの観点を1観点=1サブエージェントに配り、並列でレビューさせる
2. **評価** — 別のサブエージェントに、各指摘が誤りでないか・改善案が本当に優れているか・伝える価値があるかを評価させる
3. **統合** — あなた自身が採否を決め、正式レビューとして md に書き出す

あなたの責務は配布・評価・統合の司会であって、レビュー自体を単独で行うことではない。

## 手順

### 1. コンテキスト算出

作業リポジトリのルートで実行し、対象と出力先を確定する:

```bash
bash <skill-dir>/scripts/review-context.sh [base-branch]
```

- `base` 省略時は「PR があればその base、無ければ develop」。ユーザーが base を指定したら引数で渡す。
- 出力の `ROOT` `PR_NUMBER` `BASE_REF` `HEAD_SHA` `REL_TO_ROOT` `OUTFILE` `DIFF_CMD` と変更ファイル一覧を控える。

### 2. base の確認（必須ダイアログ）

レビューを開始する前に、`AskUserQuestion` で必ず確認を挟む:

> `<BASE>` との差分でレビューを開始します。よろしいですか？

- 解決された base（`<BASE>`）を提示し、「開始する / base を変えて再算出」を選ばせる。
- base を変える場合は、指定された base を引数に手順 1 からやり直す。
- 特に PR 未作成のブランチは develop 決め打ちで派生元を誤りやすい。この確認が唯一のガードなので省略しない。

確認が取れてから先へ進む。

`PR_NUMBER` が空の場合（PR 未作成）は、確認した base を使って**先にドラフト PR を作成してから** 再度スクリプトを実行し、PR 番号を確定させる（ユーザーの方針）。ドラフト PR の本文は `pr-description` スキルに従って書く。

### 3. 実装ルール所在の特定

`general-purpose` のサブエージェント1体だけ走らせ、この変更の照合先になる明文ルールの**ファイルパスの一覧だけ**を返させる。

**本文は返させない。** ここで本文を返させるとコンテキスト汚染回避という目的が失われる。

探させる対象:

- リポジトリルート（`<ROOT>`）の `CLAUDE.md`
- 変更ファイルが属するディレクトリ、およびその親ディレクトリの `CLAUDE.md`
- このリポジトリが使っているプラグインの規約ドキュメント。所在は次の手順で解決する。
  1. `<ROOT>/.claude/settings.json` の `enabledPlugins` から、有効なプラグイン名を得る
  2. `~/.claude/plugins/installed_plugins.json` の該当プラグインで、`projectPath` が `<ROOT>` に
     一致するエントリの `installPath` を得る（一致が無ければ `scope` が `user` のエントリ）。
     `installPath` にバージョンが含まれるので、バージョン番号を決め打ちしない
  3. その `installPath` の `docs/` 配下（サブディレクトリを含む）を探す。`docs/` が無ければそのプラグインは対象外
- 上記のうち、**コードがこうあるべきと定めている記述を含むものだけ**を返す。
  コマンドの実行方法・環境変数の設定手順・事務手続きを説明する文書は照合先にしない。
- 変更ファイルの領域（backend / frontend / test）に対応するものだけを返させる。無関係な領域は返させない。

返させる形式は1行1件、`<絶対パス> — <どの領域・どの観点向けか>` のみ。これを `RULE_FILES` として控える。

### 4. 配布レビュー（8サブエージェントを並列起動）

8つの `general-purpose` サブエージェントを**1メッセージ内で同時に**起動する。

**観点ごとの指示は起動プロンプトに書き写さない。** 各サブエージェントには、共通指示のファイルと
自分の観点のファイルを読ませる。起動側が要約・言い換えすると、文面を変えた効果が測れなくなる。

`references/perspectives/` 配下:

| 観点 | 担当 | 読ませるファイル |
| --- | --- | --- |
| 1 | 変更箇所そのもののロジック誤り | `01-logic.md` |
| 2 | 既存の呼び出し元・既存データ・過去の挙動との相互作用 | `02-interaction.md` |
| 3 | パフォーマンス | `03-performance.md` |
| 4 | 変更を入れた値の妥当性 | `04-value.md` |
| 5 | 明文ルールとの照合 | `05-rules.md` |
| 6 | テストデザインドキュメント | `06-test-design.md` |
| 7 | テストコードの忠実性 | `07-test-fidelity.md` |
| 8 | 可読性・関心の境界（命名を含む） | `08-readability.md` |

各起動プロンプトに書くのは次だけ:

- **必ず読むファイル3つ**（絶対パスで渡す）
  - `~/.claude/skills/branch-review/references/perspectives/common.md`
  - `~/.claude/skills/branch-review/references/perspectives/<担当観点のファイル>`
  - `~/.claude/skills/branch-review/references/false-positives.md`
- あなたの担当は観点N である旨
- レビュー対象の取得方法: `<DIFF_CMD>` を実行し、必要に応じて周辺コードを読むこと
- `ROOT` / `BASE_REF` / `BRANCH` / 変更ファイル一覧
- `REL_TO_ROOT` の値。該当箇所のリンクに前置させる（common.md の「該当箇所の書式」が使う）。
  **値をそのまま渡すこと。** 起動側で `../` を数え直したり書き換えたりしない
- `RULE_FILES` のパス一覧。**自分の担当観点に関係するファイルだけを Read すること**。
  規約の全文を起動プロンプトに埋め込まない
- pr-review 経由の場合のみ: 該当箇所は GitHub permalink 形式で書くこと（`HEAD_SHA` を添える。
  この場合 `REL_TO_ROOT` は使わない）

### 5. 評価（別サブエージェントに検証させる）

配布レビューで集まった全指摘と全判断ポイントを、評価担当のサブエージェント（`general-purpose`）に渡す。
同じ diff を参照できるよう `DIFF_CMD` と `RULE_FILES` も渡す。あわせて次の2つを**必ず読ませる**:

- `~/.claude/skills/branch-review/references/perspectives/common.md`（振り分け基準とフォーマット。
  レビュー担当に課したものと同じ規定で判定させるため）
- `~/.claude/skills/branch-review/references/false-positives.md`

**指摘に対する評価は3問。**

1. 事実として正しいか（誤検出・的外れでないか）
2. 改善案が提示されている指摘は、その改善案が**現行案より本当に優れているか**（トレードオフを含めて）
3. **その指摘を落としたとき、誰が、いつ、どんなコストを払うか。** これを言葉で書かせた上で、
   コストの大きさを採点させる。**水準は採点基準ファイルが定義する**（採点基準によって使う水準が違う）

第3問の採点基準は、指摘の種類ごとに独立したファイルにしてある。**評価担当には、担当する指摘に対応する
ファイルだけを読ませる。** 種類を跨いだ比較（バグと可読性のどちらが重要か）をさせないための分離なので、
関係のないファイルを渡さない。その優先順位は統合側の並び順が持つ。

| 採点基準ファイル | 対象の観点 |
| --- | --- |
| `references/scoring/bug.md` | 観点1・2・3・4 |
| `references/scoring/design.md` | 観点8 |
| `references/scoring/rules.md` | 観点5 |
| `references/scoring/test-design.md` | 観点6 |

**観点7 だけは指摘の性質で採点基準が変わる**ため、担当には `bug.md` と `rules.md` の**両方**を渡し、
振り分けも評価担当に判断させる。

- テストが誤りを見逃す性質のもの（素通りするアサーション、実データで成立しないフィクスチャ）→ `bug.md`
- テストコードとテストデザインドキュメントの記述の対応のずれ → `rules.md`

（観点7 の見直しは未了。観点6 と同じく専用の採点基準に移す予定。）

**閾値は75。** 75未満は落とす（採否は手順6 で行う。採点基準ファイルには閾値を書いていない）。

**判断ポイントに対する評価は1問。** 変更前後の挙動が具体的に示されているか
（どの条件で、何が何に変わるか）。示されていないものは却下する。判断ポイントに上記のスコアは適用しない。

各件について「支持（スコア）/ 却下 / 保留」と理由を返させる。
指摘数が多い場合は観点ごとに評価担当を分けてよいが、評価担当はレビュー担当とは別エージェントにすること。

### 6. 統合と書き出し

評価結果を踏まえ、**あなた自身が**正式レビューに載せる内容を決める。統合にあたっては:

1. **指示准拠チェック** — 各指摘が担当観点・対象 diff の範囲に沿っているか検証する
2. **範囲外の除外** — 合理性があっても、対象 diff 外や担当観点外の指摘は載せない
3. **採否** — 支持された指摘のうち、**スコア75以上のものだけを採用する**。評価で却下された指摘は落とす。
   判断ポイントは、変更前後の挙動が具体的に示されているものだけを採用する
4. **責任の自覚** — 最終 md の妥当性の責任は統合するあなたにある

**件数上限は設けない。** 閾値を満たした指摘を、順位という位置的な理由だけで落とさない。

並び順は、まず深刻度の高い順。深刻度が同じ指摘の間では、バグ → 設計・可読性 → 規約 の順に並べる。

確定した内容を `OUTFILE`（`review-<pr番号>-<連番>.md`）に書き出す。出力ディレクトリが無ければ作成する。

**書き出す直前に「最終 md の構成」と「出力の制約」を読み直すこと。** テンプレート外の欄を足す、
却下したものの記録を残す、調査した事実を書く、変更内容を語り直す——これらは書いている最中に
自然と手が伸びるもので、事前に読んだだけでは防げない。

**サブエージェントが書いた該当箇所のリンクは、そのまま転記する。** 自分で組み立て直さない。
組み立て直すと `../` の数を数え直すことになり、下のリンク検証の意味が薄れる。

#### リンクの検証（毎回・必須）

書き出したら、目視ではなく機械的に確かめる。リンク先のファイルが存在しないと、VS Code は
行番号を解釈する前に処理を打ち切るため、行へ飛ばない。壊れていても見た目では分からない。

```bash
cd "$(dirname <OUTFILE>)" && grep -oE '\]\([^)#]+' <OUTFILE> | sed 's/^](//' | sort -u \
  | while read -r p; do case "$p" in http*) continue;; esac; [ -e "$p" ] && echo "OK   $p" || echo "NG   $p"; done
```

- `NG` が1件でも出たら `REL_TO_ROOT` を確認し、全リンクを直して再検証する。
- branch-review では **`OK` が0件（リンクが1つも無い）も異常**。該当箇所がリンクになっていない。
- **pr-review 経由では該当箇所が permalink（`http` 始まり）でスキップされるため `OK` は0件が正常。**
  `NG` が0件であることと、permalink が完全な SHA を含むことを確認する。

## サブエージェント側の規定（ここには書かない）

指摘と判断ポイントの振り分け、指摘フォーマット、判断ポイントのフォーマット、該当箇所の書式は
`references/perspectives/common.md` にある。配布レビュー担当と評価担当がそれを直接読む。
**このファイルに転記しない**（二重管理になり、片方だけ直す事故が起きる）。

統合時にフォーマットを確認する必要が生じたら、common.md を読む。

## 最終 md の構成

```markdown
# レビュー: PR #<番号> (<branch> → <base>)

- 対象: `<BASE_REF>...HEAD`
- 日付: <today>

## サマリ
- 対応を要する指摘: N件
  - <指摘1の見出し>
  - <指摘2の見出し>
- 判断を要する点: M件
  - <判断ポイント1の見出し>

## 指摘

### [深刻度] 観点N — <該当箇所>
<主張（60字以内）>

- 失敗シナリオ:
- 改善案:

## 判断ポイント

### 観点N — <該当箇所>
<何がどう変わるか>

- 踏む条件:
- 判断材料:
```

## 出力の制約

- **テンプレートに定義された欄以外を追加しない。**
- **1指摘あたりの分量上限**: 見出し60字。本文200字以内（**主張・失敗シナリオ・改善案の合計**。
  主張はうち60字以内）。該当箇所は見出し側にあるので内訳に含めない。判断ポイントも同じ上限。
- **本文4KB以内を目標とする。** ただしこれは1件を短く書くことで達成する目標であり、
  閾値を満たした指摘の件数を削って達成するものではない。
- **落とすとは本文から消すこと。** 却下した指摘、対応不要と判断した項目の記録を最終 md に残さない。
  「却下した指摘」「確認済み・対応不要」に相当するセクションを作らない。
- **既に正しいと確認したものについて書かない。** 調査した事実の表示は読者の判断材料ではない
  （「なお、責務分割そのものは問題ない」「import 規約は既存の慣例に忠実」の類）。
  上と別のルールである。上は却下された指摘の話、こちらは最初から指摘ですらないものの話。
- **変更内容の語り直しをしない。** 何が変わったかの説明は PR 本文の仕事であってレビューの仕事ではない。
- **合議の経過を書かない。** 評価担当が支持したか、スコアが何点だったか、何を却下したかは
  プロセスの内部状態であって読者の判断材料ではない。「評価:」欄を復活させない。
- サマリに全体所感を書かない。件数と各件の見出しの列挙のみ。
- 見出しには観点のラベルを残す（読者がカバー範囲を判断するため）。

採用した指摘も判断ポイントも無ければ、その旨を明記した短い md を書き出す。
