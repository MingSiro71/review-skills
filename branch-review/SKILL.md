# 概要

現ブランチの変更（`origin/<base>...HEAD` の diff）をレビューし、結果を
`~/.claude/projects/<slug>/docs/review-<pr番号>-<連番>.md` に書き出す。

プロセスは3段階:

1. **配布レビュー** — 7観点を1観点=1サブエージェントに配り、並列でレビューさせる
2. **評価** — 別のサブエージェントに、各指摘が誤りでないか・改善案が現行案より本当に優れているかを評価させる
3. **統合** — あなた自身が総合判断で採否を決め、正式レビューとして md に書き出す

あなたの責務は配布・評価・統合の司会であって、レビュー自体を単独で行うことではない。

## 手順

### 1. コンテキスト算出

作業リポジトリのルートで実行し、対象と出力先を確定する:

```bash
bash <skill-dir>/scripts/review-context.sh [base-branch]
```

- `base` 省略時は「PR があればその base、無ければ develop」。ユーザーが base を指定したら引数で渡す。
- 出力の `PR_NUMBER` `BASE_REF` `OUTFILE` `DIFF_CMD` と変更ファイル一覧を控える。

### 2. base の確認（必須ダイアログ）

レビューを開始する前に、`AskUserQuestion` で必ず確認を挟む:

> `<BASE>` との差分でレビューを開始します。よろしいですか？

- 解決された base（`<BASE>`）を提示し、「開始する / base を変えて再算出」を選ばせる。
- base を変える場合は、指定された base を引数に手順 1 からやり直す。
- 特に PR 未作成のブランチは develop 決め打ちで派生元を誤りやすい。この確認が唯一のガードなので省略しない。

確認が取れてから先へ進む。

`PR_NUMBER` が空の場合（PR 未作成）は、確認した base を使って**先にドラフト PR を作成してから** 再度スクリプトを実行し、PR 番号を確定させる（ユーザーの方針）。ドラフト PR の本文は `pr-description` スキルに従って書く。

### 3. 配布レビュー（7サブエージェントを並列起動）

7つの `general-purpose` サブエージェントを**1メッセージ内で同時に**起動する。各サブエージェントには以下を必ず渡す（起動側の責務として、単独で機能するだけのコンテキストを与えること）:

- レビュー対象の取得方法: `<DIFF_CMD>` を実行し、必要に応じて周辺コードを読むこと
- `BASE_REF` / `BRANCH` / 変更ファイル一覧
- 担当観点（下記のうち1つ）
- 出力フォーマット（後述の「指摘フォーマット」）
- 指示: 対象 diff の範囲内の変更に対してのみ指摘すること。憶測ではなく該当箇所を読んで確認すること。

観点の割り当て:

- **観点1** バグの可能性があるコードはないか
- **観点2** 可読性を犠牲にしない範囲で、パフォーマンスの改善は可能か
- **観点3** メソッド名・変数名と、そのデータの型やコード上での意味がズレていないか
- **観点4** 変更を入れた値は妥当か（より根源の箇所で直すべきでないか、あるいは末端で直すべきでないか）
- **観点5** モジュール・ファイルの切り方は既存コードベースの慣例に沿っているか
- **観点6** テストデザインドキュメントが書かれているか、テストケースの切り口に過不足はないか
- **観点7** テストコードはテストデザインドキュメントのケース整理に忠実か

### 4. 評価（別サブエージェントに検証させる）

1で集まった全指摘を、評価担当のサブエージェント（`general-purpose`）に渡す。同じ diff を参照できるよう `DIFF_CMD` も渡す。評価内容:

- 各指摘は事実として正しいか（誤検出・的外れでないか）
- 改善案が提示されている指摘は、その改善案が**現行案より本当に優れているか**（トレードオフを含めて）
- 各指摘について「支持 / 却下 / 保留」と理由を返させる

指摘数が多い場合は観点ごとに評価担当を分けてよいが、評価担当はレビュー担当とは別エージェントにすること。

### 5. 統合と書き出し

評価結果を踏まえ、**あなた自身が**正式レビューに載せる指摘を決める。統合にあたっては:

1. **指示准拠チェック** — 各指摘が担当観点・対象 diff の範囲に沿っているか検証する
2. **範囲外の除外** — 合理性があっても、対象 diff 外や観点外の指摘は載せない
3. **責任の自覚** — 最終 md の妥当性の責任は統合するあなたにある。評価で却下された指摘は原則落とし、支持された指摘のみ採用する

確定した内容を `OUTFILE`（`review-<pr番号>-<連番>.md`）に書き出す。出力ディレクトリが無ければ作成する。

## 指摘フォーマット（サブエージェントに指示する形）

各指摘は以下の項目で返させる:

- 観点番号 / ファイル:行
- 指摘（何が問題か）
- 根拠（なぜそう言えるか）
- 改善案（あれば。無ければ「なし」）
- 深刻度（高 / 中 / 低）

## 最終 md の構成

```markdown
# レビュー: PR #<番号> (<branch> → <base>)

- 対象: `<BASE_REF>...HEAD`
- 日付: <today>

## サマリ
（採用した指摘の件数、深刻度の内訳、全体所感を数行）

## 指摘
### [深刻度] 観点N — <ファイル:行>
- 指摘:
- 根拠:
- 改善案:
- 評価: 支持（評価担当の要点）

（深刻度の高い順に並べる）
```

採用した指摘が無ければ、その旨を明記した短い md を書き出す。
