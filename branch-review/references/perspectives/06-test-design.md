# 観点6: テストデザインドキュメント

- **入力**: diff ＋ テスト（`*.spec.md` と対応するテストファイル）
- **採点**: 指摘の性質で分かれる
  - テストの欠落 → **バグ列**（そのテストが無いことで通り抜けるバグの大きさで採点される）
  - 記述と実装のずれ → **規約列**（照合先はテストデザインドキュメントの記述そのもの）

## 担当

- テストデザインドキュメントが書かれているか
- テストケースの切り口に過不足がないか。特に、**この変更で新たに到達可能になった経路が踏まれているか**
- 記述と実装のずれ。前提条件の記述漏れ、md が実装済みテストを過小記述している、
  md にあるケースが実装されていない

`spec.md` はテスト設計の合意文書として使われているため、記述と実装のずれ自体が問題になる。
テストが足りているかどうかだけでなく、md の記述が実装を正しく表しているかも対象。

## 必ず示すこと

テストの欠落を主張するなら、**その経路を通ると何が起こりうるか**を書く。
「カバーされていない」だけでは失敗シナリオにならない。
既にどこかで踏まれている経路なら欠落ではない。リポジトリ全体を確認してから書く。

## 担当外

テストコードが md のケース整理に忠実かどうかは**観点7**。
