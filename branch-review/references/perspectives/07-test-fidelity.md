# 観点7: テストコードの忠実性

- **入力**: テスト ＋ テストデザインドキュメント
- **採点**: `references/scoring/test-fidelity.md`

## 担当

テストデザインドキュメントは、コードから独立した**正解の照合先**として書かれている。
それを読んだ人は、そこに並ぶケースが検証済みだと理解して次の変更に入る。

これを保証するために、**ケースが、そこに書かれた主張を実際に検証しているか**を確認する。

ケース名や並び順が md と対応しているかは担当外。

### 1. 主張を検証していないアサーション

ケースは存在するが、md に書かれた主張をアサーションが押さえていない。

- 主張に対するアサーションが存在しない。主張とは別のものを検証している
- アサーションが保証できる範囲が、主張より狭い
- アサーションが条件に関係なく成立してしまう

### 2. 条件を成立させていないセットアップ

md が「〜のとき」と規定した状態、および「前提条件:」で定義された状態を、セットアップ（`let` / `let!` / `before` とファクトリ）が作り出せていない。条件が正しくなければアサーションが正しくても、そのケースを検証していることにはならない。

- 条件に対するセットアップが抜けている
- そのセットアップが、条件を満たすケースと満たさないケースの両方で成立しうる
- 条件にない制約をセットアップが課してしまっている

## 必ず示すこと

**どの入力・どの実装の誤りに対して、このテストが失敗しなくなるか**を具体的に示す。
「検証が弱い」「意図が不明瞭」だけでは失敗シナリオにならない。
壊しても通ってしまう実装の変更を1つ挙げること。

## 担当外

- **ケース名や並び順が md と対応しているか。** 突合チェッカーが機械的に検出する領域なので
  指摘しない（`false-positives.md`「linter / typechecker が捕まえるもの」と同じ理由）。
  自分でチェッカーを実行して確かめる必要もない
- **ケースの過不足、md の記述そのものの問題**（欠落・不必要・意図の取りにくさ）は**観点6**。
  観点6 は「そのケースが存在すべきか」を見て、観点7 は「存在するケースが主張を果たしているか」を見る
- 実装側のロジック誤りは**観点1・2**。テストが見逃していることではなく、実装が間違っていることを
  主張したいならそちらの担当
