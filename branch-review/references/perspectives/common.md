# 配布レビュー担当への共通指示

全観点に共通する規定。自分の担当観点のファイルと合わせて読むこと。

## 必ず守ること

- 対象 diff の範囲内の変更に対してのみ扱う。
- 憶測で書かない。該当箇所を読んで確認したことだけを書く。
- **担当観点の外は報告しない。** 観点の縄張りは排他であり、他の観点が同じ変更を別の見方で見ている。
- `~/.claude/skills/branch-review/references/false-positives.md` を必ず読み、そこに該当するものを報告しない。

## 指摘と判断ポイントの振り分け

**挙動の是非を主張するものは、誤りだと言い切れるときだけ指摘にする。** 言い切れる根拠は次の3つに限る。

1. 明文の仕様への違反
2. 明文ルールへの違反（本文を引用できること）
3. 自明な欠陥（クラッシュ、データ破壊、保存値の誤り）

これらに照らせないものは、挙動が変わることを示せても**指摘にしない。判断ポイントに回す。**
仕様にもテストにも明文ルールにも書かれていない挙動の変化は、照らす先が無いため是非を判断できない。

**この振り分けが掛かるのは、挙動が誤っていると主張する指摘だけ。** 可読性・関心の境界・命名（観点8）は
挙動の是非を主張していないので、この3根拠を満たす必要はない。読み手が払うコストを失敗シナリオとして
書けているかどうかで判定される。

## 指摘フォーマット

**失敗シナリオは必須。書けない指摘は提出しない。**

- 観点番号 / 該当箇所（後述の書式）
- 主張（何が問題か。60字以内。理由も帰結も入れない）
- 失敗シナリオ（必須）
  - バグ系: 具体的な入力・状態 → 誤った出力またはクラッシュ
  - 設計・可読性・規約系: 具体的なコスト。何が重複するか / 何が無駄になるか / 何が保守しにくくなるか / どのルールに反するか
- 根拠（なぜそう言えるか。評価担当が検証するためのもので、最終 md には載らない）
- 改善案（あれば。無ければ「なし」）
- 深刻度（高 / 中 / 低。並び順のラベルであり、採否には使われない）

## 判断ポイントのフォーマット

- 観点番号 / 該当箇所
- 何がどう変わるか（変更前 → 変更後。必須）
- どの条件で踏むか（必須）
- 構わないと判断するための材料
- **推奨は書かない。** 書いた時点で指摘に戻る

変更前後の挙動を具体的に示せないものは上げない。「判断を仰ぐ」形式は何も立証せずに書けてしまうため、
ここが唯一の門番になっている。

## 採否のされ方（知っておくこと）

評価担当が各指摘について「この指摘を落としたとき、誰が、いつ、どんなコストを払うか」を採点し、
一定の水準に達しないものは最終レビューに載らない。件数は評価されない。
失敗シナリオでコストを具体的に示せているかが分かれ目になる。数を出そうとしないこと。

## 該当箇所の書式

- 素の `src/foo/bar.ts:24` 表記に加え、絶対パスのリンクを併記する:
  `[src/foo/bar.ts:24](file:///<ROOT>/src/foo/bar.ts#L24)`
- `<ROOT>` は起動プロンプトで渡される。
- 起動プロンプトで GitHub permalink 形式を指示された場合（pr-review 経由）は、そちらに従う。
