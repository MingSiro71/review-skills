# 採点基準: 設計・可読性

**対象**: 観点8（可読性・関心の境界。命名を含む）。

## 採点

「**その指摘を落としたとき、誰が、いつ、どんなコストを払うか**」を言葉で書かせた上で、
そのコストの大きさを下の5水準で採点する。

**自然言語として解読したときの読み取りやすさで判定する。** 実行した結果ではなく、
読み手がその名前・型・配置から意図を一意に読み取れるかを見る。

**解釈のしにくさとスコープの広さは独立に見て、どちらか一方でも重ければ上の水準を採る。**
75 の条件を1つでも満たせば75。両方とも軽いときだけ50。

| 点 | 基準 |
| --- | --- |
| 0 | 好みの問題で、読み手が誤解する余地がない |
| 50 | ほかの解釈が可能だが推測が立ちやすく、かつ小さなスコープに収まっている |
| 75 | ほかの解釈が可能で、意図を一意に推測しにくいか、広いスコープに及んでいる |
| 100 | 誤解が既に起きている（既存コード内、または本 PR 内） |

### スコープ

その名前・型・判断が**有効な範囲**。JavaScript のスコープと同じ概念で範囲を定め、
**その範囲を読み切るのにどれだけ労力がかかるかで大小を判定する。**

読み手は、誤読していないことを確かめるために有効範囲の全体を見に行かされる。コストはそこで発生する。
だから範囲の外形（ブロック / 関数 / クラス / モジュール）ではなく、**その範囲を読み切る労力**で測る。

- 小さい: 有効範囲を一望できる。誤読を避けるために要する労力が小さく抑えられている
- 広い: 有効範囲を一望できない。または範囲の外まで届いていて、読み切ること自体ができない

例:

- 300行の関数の中のローカル変数 → 有効範囲が300行に及ぶので**広い**
- 40行のクラスの、2つのメソッドが使うフィールド → 有効範囲がクラス内に収まり読み切れるので**小さい**
- 他のファイル・他の層から参照できる名前 → 範囲を読み切れないので**広い**

責務の所在についての指摘では、その判断が本来の持ち主より外へ漏れているかで見る。漏れていれば広い。

## 守ること

- **ほかの採点基準と比較しない。** この基準の中での強さだけを測る。
  実行時に何も壊れないことを理由に低く採点しない。壊れないものを扱う基準である。
- **深刻度の自己申告を採点に使わない。** 高/中/低 は書き手のラベルであって価値の測定値ではない。
- 採否の閾値は起動側が持つ。ここでは採点だけを返す。
