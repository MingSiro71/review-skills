# 採点基準: テストデザインドキュメント（観点6）

**対象**: 観点6。指摘の種別ごとに基準が違うので、対応する節だけを使う。

- テストの欠落 → 「1. 欠落」
- 不必要なテスト → 「2. 不必要なテスト」
- 設定意図の取りにくい記述 → 「3. 設定意図の取りにくい記述」

共通の問いは「**その指摘を落としたとき、誰が、いつ、どんなコストを払うか**」。
これを言葉で書かせた上で、対応する節の水準で採点する。

## 1. 欠落

検証されていない仕様が**将来壊れたときの実害**と、壊れる見込みで測る。
検証が無いので、壊れても気づけない。

| 点 | 基準 |
| --- | --- |
| 0 | 仕様ではない（偶然そのような挙動になっているが何ら重要ではない） |
| 50 | 仕様として守るべき範囲は検証されている。それ以上細かく見ることもできるがさほど重要でない |
| 75 | 仕様として守るべきことが検証されていない |
| 100 | 通常の利用で保証されるべき仕様が検証されていない |

## 2. 不必要なテスト

そのテストに価値があるか。価値が極めて低いテストはコストにしかならない。

| 点 | 基準 |
| --- | --- |
| 0 | 仕様を正確に表し、重複もないテストである |
| 50 | 仕様を正確に表している。他と検証内容が重複しているがテスト観点は違ったり、包含関係にあるが1つ手前のステップのテストとみなすことができる |
| 75 | 仕様として重要性のない現挙動をトレースしているだけのテストであるか、完全に重複している |
| 100 | 常に真となるなど、何も検証できていない |

## 3. 設定意図の取りにくい記述

仕様に対して読み手が誤った理解を持ちうるか、理解が届かないような内容の定義は意味がない。
特に誤った理解を与えるものは無価値であるどころか害がある。

| 点 | 基準 |
| --- | --- |
| 0 | 読んで仕様を正しく理解できる（表記の揺れ、体裁の差） |
| 50 | 単体では正しく理解しにくいが、周辺のテストや補足を読めば容易に正しい理解ができる |
| 75 | 理解不能であるか、誤った解釈をしてしまう。検証したい仕様に対して、結論は同じだが誤った視点で解釈してしまうものも含む |
| 100 | 仕様に反しているか、どう解釈しても仕様に合致すると言えない |

## 守ること

- **ほかの採点基準と比較しない。** この基準の中での強さだけを測る。
  節をまたいだ比較（欠落と重複のどちらが重いか）もしない。指摘の種別に対応する節だけで採点する。
- **「実装を読めば分かる」を軽い側の理由にしない。** 読み手はテストデザインドキュメントを読んで
  仕様を把握する。実装を読み直せば復元できることは、ここでは緩和材料にならない。
- **深刻度の自己申告を採点に使わない。** 高/中/低 は書き手のラベルであって価値の測定値ではない。
- 採否の閾値は起動側が持つ。ここでは採点だけを返す。
