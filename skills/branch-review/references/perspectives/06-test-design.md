# 観点6: テストデザインドキュメント

- **入力**: diff ＋ テスト（`*.spec.md` と対応するテストファイル）
- **採点**: `references/scoring/test-design.md`

## 担当

- このテストが実装の仕様を過不足なく表現できているか
- のちにメンテナンスする人が、今のドキュメントに対して足す・直す・消す・そのままにするの判断を正しく下せるか

を保証するため、以下の視点から評価する。

### 1. テストの欠落

作成、または変更されたコードが持つ仕様を表現するテストが存在するか。

検証されていない仕様を、検証されていると思ったまま次の変更が入ることはリスクである。

### 2. 不必要なテスト

- 同じ経路を、別のケースが重ねて踏んでいる
- 実装の内部構造を写しただけで、推測される仕様上の主張からすればどちらでも構わないものである
- 仕様上ありえない条件を組み立てている

消してよいか判断できないまま維持され、実装を変えるたびに直すコストを生む。

### 3. 設定意図の取りにくい記述

- そのケースが何を確かめるためのものか書かれていない
- あたかも別の観点から検証しているかのような記述である
- 条件で指定されている値が、なぜその値なのかを読み取れない

意図が読み取れないケースは、仕様の説明力を持たずテストの有効性を評価しにくくなる。

## 必ず示すこと

- **欠落**を主張するなら、その影響を考える。「カバーされていない」だけでは失敗シナリオにならない。最終的に何が起こるのかまで追跡する。
- **不必要**を主張するなら、そのケースが無くなっても何が守られ続けるか
- **意図が取れない**ことを主張するなら、読み手に知らせるべき仕様は何で、記述のどこが合わないか

## 担当外

ケースが、そこに書かれた主張を実際に検証しているか（主張を押さえていないアサーション、
条件を成立させていないセットアップ）は**観点7**。観点6 は「そのケースが存在すべきか」を見て、
観点7 は「存在するケースが主張を果たしているか」を見る。
