# 採点基準: テストコードの忠実性（観点7）

**対象**: 観点7。

共通の問いは「**その指摘を落としたとき、誰が、いつ、どんなコストを払うか**」。
これを言葉で書かせた上で、下の水準で採点する。

## 採点

測るのは「**そのケースが検証済みとして扱われ続けることで、通り抜ける誤りの大きさ**」。

テストデザインドキュメントに並んだケースは、読んだ人に検証済みだと理解される。
検証していないケースは、単に無いよりも悪い。無ければいずれ足されるが、
あるように見えているものは二度と足されない。

観点7 の2つの問題（主張を検証していないアサーション / 条件を成立させていないセットアップ）は、
どちらも「ケースは存在し、md とも対応しているのに、その主張を検証していない」という同じ状態を作る。
コストの発生源が同じなので、節を分けずに一本の水準で採点する。

| 点 | 基準 |
| --- | --- |
| 0 | ケースは主張を検証している（書き方の好み、より強い書き方があるという程度の差） |
| 25 | 論理的には検証が主張をカバーしきれていない部分があるが、ミドルウェアやフレームワーク等の技術的基盤の制約から漏れはないと言える |
| 50 | 技術的基盤の制約を含めても論理的に検証が主張をカバーしきれていない部分があるが、一般的かつプロジェクト内で守られているプラクティスに沿えば漏れはないと言える |
| 75 | 検証が主張をカバーしきれていない部分がある |
| 100 | 検証が主張を何もカバーしていない |

## 守ること

- **ほかの採点基準と比較しない。** この基準の中での強さだけを測る。
  採点基準を跨いだ優先順位は統合側の並び順が持つ。
- **25・50 に下げてよいのは、漏れを塞ぐものを名指しできるときだけ。** 技術的基盤なら、どの
  ミドルウェア・フレームワークのどの挙動が塞ぐのかを示す。プラクティスなら、プロジェクト内の
  他の箇所を見て、実際に守られていることを確かめる。**名指しできなければ下げない。**
- **次のことは緩和材料にならない。**
  - テストが通っていること（誤りを見逃すテストは、見逃している間ずっと通る）
  - ほかのケースが同じ誤りを捕まえること（この基準が測るのは、そのケースが自分の主張を果たしているかである）
- **深刻度の自己申告を採点に使わない。** 高/中/低 は書き手のラベルであって価値の測定値ではない。
- 採否の閾値は起動側が持つ。ここでは採点だけを返す。
